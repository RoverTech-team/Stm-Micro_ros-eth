Replace the arm directory with the quasi-working BRINGUP setup

Swap the current in-tree arm firmware (CM7_arm + CM7_arm_e2e + CM4) for the self-contained, step-gated BRINGUP variants (cm7_e2e_full + cm4_full, rollback cm7_echo + cm4_follow). This is a plan only — no files are moved or deleted by this document.

Type: Replacement Plan Scope: microroseth/CM7_arm, CM7_arm_e2e, CM4 → microroseth/BRINGUP Destructive: yes (dir replacement) Requires: bench + ST-Link + Jetson

01 Executive Summary

The microroseth/ arm firmware tree (CM7_arm/, CM7_arm_e2e/, CM4/, built via microroseth/Makefile/) is the active but unvalidated working copy. The BRINGUP/ tree holds the quasi-working setups that were last confirmed moving the arm on hardware (eyewitness, 2026-09-05): cm7_e2e/cm4_follow for step 2 (J1–J5 ±10°, J6 held) and cm7_e2e_full/cm4_full for step 3 (all 6 joints, attended).

This plan defines how to replace the `arm` directory with the BRINGUP setup: back up the current tree, swap in BRINGUP variants as the canonical arm firmware, rebuild per-variant, flash via ST-Link, and validate through the gated step1→step2→step3 runbook — with instant rollback to the proven echo/net baseline.

Today (arm dir)

microroseth/CM7_arm + CM7_arm_e2e + CM4
  • CubeMX-style (.ioc), shared Makefile/ builds
  • CM7_arm reference.c is Arduino pump stub (not arm motion)
  • No step gating, no instant rollback
  • Last confirmed motion: none on BRINGUP-equivalent

Target (BRINGUP)

microroseth/BRINGUP/{cm7_e2e_full,cm4_full}
  • Self-contained Makefile + build/ per variant
  • Shared SRAM .shared @0x38000000, magic 0x53485244 v2
  • Gated: step1 echo → step2 J1–J5 → step3 full (attended)
  • Instant rollback: flash_echo.sh (~1 min)

Decision needed

Approve before any mv/rm
  • Confirm which BRINGUP variants become canonical
  • Confirm backup location + rollback trigger
  • Confirm bench + Jetson + ST-Link availability

⚠ reference.c is not arm motion

CM7_arm/reference.c is an Arduino pump-duty-cycle stub (GPIO/Serial only) — it is not part of the STM32H7 arm bringup and should not be carried forward unless intentionally ported.

No validated motion in the arm dir

The in-tree CM7_arm/CM7_arm_e2e/CM4 have not been the source of the last confirmed arm motion. The confirmed motion came from BRINGUP/cm7_e2e + cm4_follow (step 2) on 2026-09-05. Replacing the arm dir with BRINGUP is therefore a move toward the last-known-good configuration, not away from it.

05 Why BRINGUP — evidence

  • Last confirmed motion: step 2 (cm7_e2e + cm4_follow) validated 2026-09-05 — seq=1,2,3 landed (mdeg=±9998, ack 0→1→2), arm physically moving (eyewitness).
  • Self-contained: each variant has its own Makefile + build/; rollback = rebuild + flash the other variant, no shared build state.
  • Gated runbook: STEPS.md enforces step1→step2→step3; do not advance on FAIL.
  • Instant rollback: flash_echo.sh returns to proven ping+echo in ~1 minute.
  • Single-source main.c: all 3 CM7 `main.c` byte-identical (behavior via -DBRINGUP_E2E=0/1 -DBRINGUP_J6_HOLD=0/1); both CM4 `main.c` identical (J6 hold via flag). Safe defaults (E2E=0, J6_HOLD=1) if flags absent.
Vendor-tree references

cm4_follow references vendor trees relatively (../../../../H7-Arm/H7arm/{Drivers,Middlewares,Common}); CM7 variants are self-contained except ../../micro_ros_stm32cubemx_utils (stable). Verify these relative paths resolve after the swap before building.

06 Execution phases

1

Phase 1 — Backup & freeze · 15 min · no bench

  • Commit or tar the current arm dir: CM7_arm/, CM7_arm_e2e/, CM4/, Makefile/CM7_arm, Makefile/CM7_arm_e2e, Makefile/CM4 → backups/arm_tree_20261116.tar.gz
  • Record current flashed images + sizes (baseline for rollback comparison).
  • Freeze: no edits to the arm dir during the swap.
2

Phase 2 — Swap directories · 10 min · no bench

  • Remove/retire CM7_arm/, CM7_arm_e2e/, CM4/ and their per-dir Makefile/ entries.
  • Adopt BRINGUP/ (cm7_echo/cm7_e2e_full/cm4_full/cm4_follow) as the canonical arm firmware.
  • Confirm relative vendor paths (../../../../H7-Arm/H7arm/…, ../../micro_ros_stm32cubemx_utils) resolve from the new locations.
3

Phase 3 — Build · 20 min · offline-safe

  • make -C microroseth/BRINGUP all -j4 (builds all 5 variants).
  • make -C microroseth/BRINGUP manifest to regenerate BUILD_MANIFEST.md (sizes + sha256).
  • Confirm sizes match manifest (cm7_e2e_full 147228/1048/410564, cm4_full 14640/388/2148).
4

Phase 4 — Flash & validate · bench + Jetson + ST-Link

  • Flash step 1 baseline: make step1 (cm7_echo + cm4_follow).
  • Validate net: make test-net (ping 192.168.0.5, ARP 00:80:e1:00:00:00, /heartbeat).
  • Advance to step 2 (cm7_e2e + cm4_follow): J1–J5 ±10°, J6 held.
  • Advance to step 3 (cm7_e2e_full + cm4_full, attended, type YES): all 6 joints ±10°.
5

Phase 5 — Cutover & sign-off · 10 min

  • Update microroseth/README.md and any references pointing at CM7_arm//CM4/ to point at BRINGUP/ variants.
  • Record final flashed image names/sizes; close the backup or keep as rollback source.

08 Rollback plan

  • Instant: ./microroseth/BRINGUP/scripts/flash_echo.sh → back to proven ping+echo (cm7_echo + cm4_follow) in ~1 minute.
  • Tree rollback: restore backups/arm_tree_20261116.tar.gz into microroseth/ (CM7_arm, CM7_arm_e2e, CM4, Makefile/ entries).
  • Trigger: any step gate FAIL, unexplained all-motion-dead, or J1/J3/J5 behavior worse than the 04_11_26.md baseline.
  • Full-erase caveat: if motion dies after repeated SW-reset flashes, do a mass-erase (-e all) + reflash + reset before suspecting code (a binary that moved after full erase proved it was latch state, not firmware).
