RFC · microrosWs/microk3 · new capability

Publish any topic from the browser.
Drive the rover like a gamepad.

Add a Topic Publisher Studio (sliders, toggles, joysticks, enum selects) and a dedicated Teleop Drive console to MicroK3 — both publishing real ROS 2 messages, with /cmd_vel teleop under the hood. No firmware change; just a new, joyful web layer on top of the existing micro-ROS graph.

Type: Feature Plan Scope: microk3 + ros_interface Effort: ~10 days No firmware change

01 Executive Summary

Today MicroK3 is read-mostly: it watches topics, displays them, but cannot drive anything. Operators must drop to a terminal and run ros2 topic pub or teleop_twist_keyboard.

This plan adds two complementary publisher surfaces:

⦿ A — Publisher Studio NEW PAGE

/command — generic publisher

Pick any topic + type from the ROS graph, get an auto-generated form (sliders, toggles, selects, vector editors). Publish once, or stream at a rate. Save as a preset. Think "ROS topic pub, but beautiful".

  • Supports std_msgs, geometry_msgs, sensor_msgs + any discovered type via reflection
  • Sliders for numeric ranges, toggles for bools, color pickers for displays, XY pads for vectors
  • Live echo of what was actually published

◉ B — Teleop Drive NEW PAGE

/drive — rover teleop, uses teleop under the hood

A focused driving console that publishes geometry_msgs/Twist to /cmd_vel (and configurable topic). Virtual joystick + D-pad + WASD + gamepad, with dead-man, turbo, and an emergency stop. Feels like a drone controller, not a form.

  • Four input modes unified to one Twist publisher
  • Rate-limited (10–50 Hz), latched stop on release
  • Visual odometry / velocity feedback strip
✅ The invariant

Both surfaces are pure publishers — they reuse the existing MicroK3RosNode publisher pattern (today: microk3/commands). No new transport, no firmware contract change. The browser never talks DDS directly; Flask validates, rate-limits, and the ROS node publishes.

06 Feature A — Topic Publisher Studio

06.1 What it does

Let an operator pick any discovered topic (or type a new one), get an auto-generated, typed control panel, and publish.

Topic picker

  • Dropdown of get_topic_names_and_types() results (searchable), plus "Custom topic" free-text.
  • Type resolved via rosidl_runtime_py.get_message(type) — same as the watch path.
  • If type unknown, falls back to raw JSON editor with schema hint.

Control generation

  • Walk message_to_ordereddict field tree → render control per leaf.
  • float/int → slider + number input (editable min/max/step)
  • bool → toggle, string enum → segmented, array → repeatable rows
  • geometry_msgs/Vector3 → XY pad + Z slider; Twist → dual XY pads

06.2 Publish modes

ModeBehaviorUse case
OnceSingle publish() on clickSet a mode, trigger an action
StreamPublish at chosen rate (1–30 Hz) while active; stop button / toggle off stopsHold a velocity, sweep a joint
LatchedPublish once with latch=true semantics (republish on new subscriber via ROS QoS transient_local)Config topics that new nodes should see

06.3 Presets

Save the full panel state (topic + field values + mode + rate) as a named preset in localStorage + optional server persistence (data/publisher_presets.json). Presets show as chips; click to load, publish in one tap. Export/import JSON.

06.4 Live feedback

Below the publish bar: last publish timestamp, echoed message (pretty JSON), and any ROS error. If the topic is also watched, its live card updates in place — user sees the round-trip.

07 Feature B — Teleop Drive (Teleop Under the Hood)

Under the hood = teleop_twist_keyboard logic, in the browser

The page publishes geometry_msgs/msg/Twist to /cmd_vel exactly like teleop_twist_keyboard does — linear.x + angular.z, stamped at a fixed rate, with zero on release. It is not a wrapper that shells out; it is the same Twist math, just driven by a joystick/keyboard/gamepad instead of stdin.

07.1 Input modes (all converge to one Twist publisher)

1 · Virtual joystick

Drag puck: Y → linear.x (−max…+max), X → angular.z. Spring-return to zero on release (with E-stop style hard stop). Works with mouse + touch.

Uses a small pointerdown/move/up handler + requestAnimationFrame clamp; publishes at the selected rate (default 20 Hz).

2 · D-pad / Buttons

Hold ▲/▼ to ramp linear, ◀/▶ to ramp angular. Press duration = velocity (first press = 30% max, hold → ramp to 100%). Release → zero.

3 · Keyboard (WASD + Arrows)

W/S or ↑/↓ → linear, A/D or ←/→ → angular, Space = immediate stop, Shift = turbo (×1.8). Requires dead-man: holding Space not needed, but releasing all keys auto-stops after 150 ms.

4 · Gamepad (optional)

Browser Gamepad API: left stick → same mapping as joystick. Detected automatically; badge shows "Gamepad: Connected (Xbox)". Falls back gracefully when absent.

07.2 Twist mapping

# Unified producer — every input mode calls this
def twist(linear_x: float, angular_z: float) -> Twist:
    msg = Twist()
    msg.linear.x  = clamp(linear_x,  -max_linear,  max_linear)
    msg.angular.z = clamp(angular_z, -max_angular, max_angular)
    # all other fields = 0 (rover is differential-drive)
    return msg

# Published at fixed rate while active; one final zero Twist on stop/E-stop/blur

07.3 Safety

GuardHow
Dead-manJoystick must be held / key held / gamepad stick deflected. Releasing any → publish zero within 100 ms. Window blur also fires zero.
WatchdogIf the browser stops publishing for > 500 ms, ROS node auto-publishes zero (timer on server). Covers tab crash / network drop.
Rate limitClient capped at 50 Hz, server ignores > 50 Hz per session. Slider caps for max velocities (configurable).
E-stopBig red button → immediate zero + cancels stream timer, requires re-arm (click again) to drive.
AuthBoth pages & API require operator role (or admin). Anonymous is read-only.
Topic allowlist/cmd_vel default; optional TELEOP_ALLOWED_TOPICS=/cmd_vel,/rover/cmd_vel env.

07.4 Feedback strip

Below the joystick: live linear.x / angular.z numeric readouts + a horizontal velocity bar (cyan → amber at >80% max). If odometry is available (/odom watched), show a tiny sparkline of actual vs commanded velocity — reuse the existing watch plumbing read-only.

No DDS from the browser

The browser never creates a ROS publisher. It POSTs JSON to Flask; Flask validates + clamps, then the MicroK3RosNode publishes via rclpy. This keeps auth, rate-limiting, and allowlisting server-side and avoids exposing DDS to the frontend.

10 Safety & Security

Auth & rate limits

  • Both pages behind @auth.login_required + role check (operator minimum). Viewer role is read-only.
  • Publish endpoints: 30/min for once, 120/min for teleop stream (server enforces per-IP + per-session).
  • Allowlist: TELEOP_ALLOWED_TOPICS env; generic publish allowlist optional (PUBLISH_ALLOWED_TOPICS="*" default, restrict in prod).

Operational safety

  • Teleop watchdog: if no /teleop POST within 500 ms while "armed", server publishes zero and disarms.
  • Client dead-man: releasing joystick/keys publishes zero immediately; visibilitychange + blur also stop.
  • Audit: each publish logs user, topic, payload hash, timestamp to app.log (structured).
E-stop is not a suggestion

The red E-stop is always visible on /drive, bound to Space and Esc as well. It publishes a zero Twist and cancels any stream timer, requiring an explicit re-arm click before driving resumes.
