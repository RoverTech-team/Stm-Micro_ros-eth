H7-Arm Audit · WireTest standalone PASS → Jetson topic command FAIL — clarified

Why WireTest moves but the Jetson topic command does not

Standalone CM4_wiretest / WIRE_TEST firmware rocks the motor at ±10° proving SPI chain, powerSTEP01 config, and wiring are healthy. The same hardware ignores normal Jetson topic commands on /hardware_level/commands (JointState) → arm_bridge → /joint_commands (Float32MultiArray) → CM7 ParseJointCommand() → SRAM4 → CM4 Motor_ProcessCommands(). This report ranks the 10 most probable root causes for topic-command failure with file-anchored evidence and concrete fixes. No code was modified.

#1

Wrong CM4 binary flashed — Jetson topic commands ignored by design WireTest builds never read SRAM4; only cmdfollow does

Probability: 38% — System designCRITICAL

Evidence

  • CM4/Core/Src/main.c:24-26 #ifndef WIRE_TEST / #define WIRE_TEST 1 — when enabled, Motor_ProcessCommands() is compiled out (main.c:180 #if !WIRE_TEST).
  • main.c:301-315 the loop rocks RARM_MoveDegrees(5,±10) and never reads joint_cmd_seq — Jetson /joint_commands is dead in this build.
  • main_wiretest.c:1-14 explicitly: Ignores shared-memory commands... Change TEST_SW_IDX to discover wiring. — standalone bench test, no topic path.
  • CM4_standalone / main_cmdfollow.c is the only build that follows Jetson topic commands (always cmd-follow, no wiretest code).
  • Operator sequence: WireTest PASS was likely CM4_wiretest or CM4 (WIRE_TEST=1); immediate Jetson topic test without reflashing to CM4_standalone will always show seq:0 ack:0.
Clarified symptom match: WireTest PASS proves motors/SPI/24V are healthy. Jetson /hardware_level/commands → /joint_commands topic commands fail only when the CM4 still runs a WireTest build — CM7 may even parse (joint-cmd-recv) but CM4 never consumes joint_cmd_seq.
What the three binaries actually do 
Makefile/CM4            → main.c  (WIRE_TEST=1 default) → autonomous rock, IGNORES topic SRAM4
Makefile/CM4_wiretest   → main_wiretest.c (TEST_SW_IDX=1) → autonomous rock, IGNORES topic SRAM4
Makefile/CM4_standalone → main_cmdfollow.c → FOLLOWS Jetson topic via SRAM4 — flash this for topic tests

Proposed fix

  1. Flash the correct binary for topic tests: make -C Makefile/CM4_standalone && arm-none-eabi-objcopy … && STM32_Programmer_CLI -c port=SWD -w build/MicroRosEth_CM4_standalone.elf -v then re-test Jetson topic.
  2. Future: runtime wiretest gate instead of compile-time: add shared_data_t.wiretest_enable or /wiretest_cmd topic so bench rock and topic follow coexist in one binary.
  3. Document the flashing matrix in H7-Arm/README.md and print the active build id at boot (CM4: build=wiretest|cmdfollow).
Effort: 1–2 h · Risk: Low · Validates via seq/ack diag + physical observation.
#2

Joint-count mismatch: Jetson sends 3 joints, CM7 expects 6 9-float payload misaligns positions vs velocities → wrong mdeg

Probability: 31% — Data planeCRITICAL

Evidence

  • arm_bridge.py:22 JOINT_NAMES = ["joint_1","joint_2","joint_3"], arm_bridge.py:84 out.data = pos+vel+eff → 9 floats.
  • CM7/main.c:58 JOINT_COUNT 6u, CM7/main.c:382 if(data.size < JOINT_COUNT) return; → 9 passes, but
  • CM7/main.c:387-389 positions[i]=data[i] for i 0..5 → data[3..5] are actually velocities for J1..J3, polluting J4..J6 positions.
  • CM7/main.c:392-397 velocities[i]=data[6+i] → grabs eff0..eff2 plus out-of-bounds reads for i=3..5 (uninitialized trailing floats).
  • CM7/main.c:425-428 writes only SHARED_JOINT_COUNT (=6) positions derived from the corrupted array.
  • Reverse path: arm_bridge.py:59 checks len(d)<9 then slices d[0:3], d[3:6], d[6:9] but CM7 publishes 18 floats (CM7/main.c:500 size=JOINT_COUNT*3=18).
Concrete effect: Sending JointState position [0.1,0.2,0.3] rad for J1..J3 yields SRAM4 mdeg [5729,11459,17188, 0,0,0] plus garbage — if vel/eff are zero the extra positions are near-zero, so J4..J6 get ~0 delta and never move; the operator rocks J2/J5 and sees nothing.

Proposed fix

  1. Align N: either expand JOINT_NAMES to 6 (joint_1..joint_6) or make CM7's JOINT_COUNT parametric and pad missing joints with last-known or zero. Recommended: arm_bridge.py pads to 6 before publish, CM7 accepts size==9 as N=3 and mirrors it to the correct PHYS_* slots.
  2. Add guard: ParseJointCommand should reject or pad when size != 6 && size != 9 && size != 18 and log joint-cmd-size-mismatch.
  3. Test: ros2 topic echo /joint_commands --field data on Jetson must show 18 floats after fix.
Effort: 30 min · Risk: Low · Breaks nothing; fixes both command and state paths.
#3

Latched fault permanently gates motion in cmd-follow builds main_cmdfollow silently skips faulted joints forever

Probability: 27% — Firmware logicCRITICAL

Evidence

  • main_cmdfollow.c:389-391 if(rr_faults[i]!=0) continue; — no clear, no retry.
  • main.c:407-414 (the non-wiretest main.c) does clear: ps01SetAlarms_chain(...); rr_faults[i]=0; before retry — so the two binaries diverge.
  • main_cmdfollow.c:420-435 faults are only cleared on button press; main_cmdfollow.c:420-443 RR_PollFaults re-latches STALL/UVLO every 10 ms.
  • CM4/debug.md: Fix #7/#8 documents latched STATUS bits (UVLO at 24 V ramp, STALL on first move) that transiently set fault_alarm and are never cleared in cmdfollow.
  • In logs: f:0x… code:… st:… shows non-zero status that persists after power-on.
Why WireTest still passes: WireTest never checks rr_faults before RARM_MoveDegrees; cmd-follow does. So hardware is fine but Jetson commands are swallowed.

Proposed fix

  1. Port the fault-tolerant logic from main.c:407 into main_cmdfollow.c: clear transient ALARM_STALL|CMD_ERR|OVC|THRM|UVLO and reset rr_faults[i] before each retry; real OC/thermal re-latches next poll and still protects hardware.
  2. Alternatively, reset rr_faults after the 2 s stabilization delay or after the button-cleared path.
  3. Add a fault_gated_moves_skipped counter to shared_data for CM7 diag.
Effort: 15 min · Risk: Low — already proven in main.c variant.
#4

Physical daisy-chain index ≠ logical joint index Jetson J2 command goes to wrong driver chip

Probability: 22%HIGH

Evidence

  • main_wiretest.c:57-70 and main_cmdfollow.c:57-64 define PHYS_J1=0, PHYS_J5=1, PHYS_J6=2, PHYS_J4=3, PHYS_J3=4, PHYS_J2=5 — the validated sweep order.
  • rarm.h originally had a different order; CM4/debug.md: Fix #3 fixed it to sequential but the PHYS_* remap is still required.
  • main_wiretest.c:14 TEST_SW_IDX 1 rocks PHYS_J5, not J2 — operator must change it per joint.
  • CM7/main.c:425 writes joint_cmd_positions[i] for i 0..5 in logical J1..J6 order; CM4 interprets i directly as daisy-chain position — if the PHYS_* map is not applied on the CM4 side for commands, J1 command hits chip 0 (correct) but J2 command hits chip 1 (actually J5 hardware).
Observation: WireTest on TEST_SW_IDX=1 moves J5 visibly; Jetson topic publishing joint_2=10° (logical index 1) writes positions[1] which CM4 drives as chip 1 → also J5 → the operator watching J2 sees no motion and reports "Jetson topic command failed".

Proposed fix

  1. Unify the index contract: either make CM7 translate logical → physical before writing SRAM4, or make CM4's Motor_ProcessCommands index through a LOGICAL_TO_PHYS[6] map. Document which joint is which in pin-mapping.md.
  2. Expose the map in /joint_states metadata (URDF) so RViz and the Jetson agree on names.
#5

DDS QoS incompatibility — command never arrives at CM7 Reliable vs Best-Effort mismatch still possible on Jetson

Probability: 18%HIGH

Evidence

  • CM7/main.c:1364-1396 joint_commands_subscription = rclc_subscription_init_default (reliable) + executor size 1.
  • arm_bridge.py:50-52 create_publisher(Float32MultiArray, COMMANDS_OUTPUT_TOPIC, 10) defaults to reliable — matches, but some Jetson images override QoS via env or use BEST_EFFORT profile.
  • Session history notes joint_commands best_effort vs host reliable was the delivery break — now fixed — but only on the Mac host; Jetson may still carry the old profile.
  • Reverse path is deliberately BEST_EFFORT: CM7/main.c:1351-1356 rclc_publisher_init_best_effort + arm_bridge.py:45 BEST_EFFORT sub — correct.
Check: ros2 topic info /joint_commands -v on Jetson must show publisher reliability RELIABLE and subscription RELIABLE. If Jetson shows BEST_EFFORT, DDS will never match and JointCommandCallback never fires (no CM7: joint-cmd-recv log).

Proposed fix

  1. On Jetson, force arm_bridge.py publisher QoS to QoSProfile(depth=10, reliability=ReliabilityPolicy.RELIABLE) or leave default (reliable) — do not set best-effort.
  2. Add a CM7 boot log CM7: joint-commands-qos=reliable and a Jetson-side ros2 doctor check in bringup.
#6

SRAM4 cache coherency + sequence race Dirty DCache never cleaned or torn read

Probability: 14%MEDIUM

Evidence

  • CM7/main.c:431-434 SCB_CleanDCache_by_Addr cleans only joint_cmd_positions + joint_cmd_seq — but not the whole struct; stale lines can persist.
  • CM7/main.c:498-499 correctly invalidates joint_act_positions before reading.
  • CM4/main_cmdfollow.c:358-360 seq_a / DMB / seq_b torn-read guard — but CM4 is Cortex-M4 bare-metal with DCache disabled by default; __DMB/__DSB ordering matters and HAL_GetTick vs DWT timing are mixed sources.
  • shared_data.h:14 struct is not packed or cache-line aligned; it straddles lines.
Failure mode: CM7 writes new joint_cmd_seq but the cache line containing it is still dirty in CM7's DCache; CM4 reads old seq (0) forever. WireTest never reads SRAM4 so it never fails.

Proposed fix

  1. Clean the entire shared_data_t or at least a 32-byte aligned region covering joint_cmd_positions..joint_cmd_seq with correct size alignment.
  2. On CM4, add SCB_InvalidateDCache_by_Addr for joint_cmd_positions/seq if M4 DCache is enabled (check CCR.DC), or disable DCache for the SRAM4 region via MPU.
  3. Add a diagnostic: CM7 prints clean-addr/size at boot.
#7

Magic/version gate blocks all commands CM7 silent early-return on mismatch

Probability: 12%MEDIUM

Evidence

  • CM7/main.c:371-375 if(magic!=SHARED_MAGIC || version!=SHARED_VERSION) return; — no log, no increment of seq.
  • CM4/.../main*.c:221-224 zeroes then sets magic=0x53485244 version=2 — but if CM4 reboots after CM7, CM7 sees transitional zeros and drops commands until next boot message.
  • CM7 diag protocol-mismatch got=… expected=… — refusing commands (CM7/main.c:1635) only prints once at boot, not per dropped command.

Proposed fix

  1. Log every dropped command with reason (magic-mismatch) at DEBUG level, and expose shared_data.magic/version in the 1 Hz CM7 diag line.
  2. Add a "re-sync" check: if joint_cmd_seq advances but magic mismatches, re-read magic after DCache invalidate.
  3. Ensure both cores include the same shared_data.h (today they are duplicated files that can drift).
#8

Unit trap: radians vs degrees vs milli-degrees Small Jetson command rounds to zero steps

Probability: 11%MEDIUM

Evidence

  • CM7/main.c:428 mdeg = lroundf(rad * 1000 * 57.2957) (rad→mdeg).
  • rarm.c:104-133 RARM_MoveMilliDegrees clamps to min/max_degs*1000 then computes steps = delta*mdeg * steps_rev*(1<<microsteps)*ratio /360000; delta < ~1–2 mdeg can round to 0 steps and ps01Move_chain is skipped.
  • If Jetson sends 0.01 rad (~0.57°), mdeg=573, delta may be ~20 steps before gearing — but with ratio 50 and 128 microsteps it is ~hundreds, so visible. If it sends 0.001 rad or already-converted degrees, delta rounds to 0 and nothing moves.
  • WireTest uses integer degrees (RARM_MoveDegrees(…,10)) — never hits rounding edge.

Proposed fix

  1. Enforce and document: Jetson must publish radians on /hardware_level/commands (ros2_control convention). Add a range assert in arm_bridge.py on_commands: warn if abs(pos)>6.28 (likely degrees).
  2. Log the computed delta_mdeg and steps on CM4 when debug is enabled.
  3. Consider a cmdfollow deadband: ignore |delta|<5 mdeg but report it as delta_below_threshold in diag.
#9

Brake interlock holds J2/J3 even though command targets them WireTest releases brakes; cmd-follow may not

Probability: 10%MEDIUM

Evidence

  • main_wiretest.c:298-299 releases both brakes every loop unconditionally.
  • main_cmdfollow.c:393-401 only releases if i==PHYS_J2 || i==PHYS_J3 and only when delta!=0 and rr_faults==0.
  • If the Jetson topic moves J5 (which has no brake) the brake path is fine — but if it moves J2/J3 and the fault gate (#3) fired first, the brake release is skipped and the motor fights a holding brake.
  • main_cmdfollow.c:376-378 re-engages brake after BRAKE_SETTLE_MS 100ms of stillness — if the next Jetson command arrives within 100 ms the brake never re-engages; if it arrives after, there is a 100 ms window where the motor is braked and the new delta is ignored.

Proposed fix

  1. Ensure brake release happens before the fault gate, or clear faults first (see #3).
  2. Expose brake_state in CM7 diag (already does: brk:… at CM7/main.c:597) and require operator to check brk:0 before declaring "no motion".
  3. Add a Jetson-side /brake_release service for bench tests.
#10

Micro-ROS executor starved by publisher mutex joint_commands callback never runs

Probability: 9%LOW

Evidence

  • CM7/main.c:629-631 rclc_executor_spin_some(...,20ms) holds microros_mutex; CM7/main.c:577-582 heartbeat publisher also holds it; both tasks are osPriorityNormal.
  • CM7/main.c:1487-1505 mutex is osMutexRecursive but not priority-inheriting.
  • If heartbeat publish blocks (agent latency), the executor is starved for >20 ms and DDS samples are dropped (best-effort queue depth 1).
  • CM7/main.c:520-527 JointCommandCallback prints joint-cmd-recv / joint-cmd-parsed — absence of these lines in serial capture is the smoking gun for starvation vs QoS (#5).
Distinguish #5 vs #10: No joint-cmd-recv + no DDS match → #5 (QoS). No joint-cmd-recv + DDS matched but publish-ok stalls → #10 (mutex).

Proposed fix

  1. Raise JointCmdExec priority above HeartbeatPub or use a separate mutex for subscriptions vs publications.
  2. Reduce executor hold time: spin with 5 ms timeout and yield, or use rclc_executor_spin in a dedicated thread without the shared mutex (micro-ROS is thread-safe per context when serialized correctly).
  3. Add a executor_spins / callbacks_fired counter to the 1 Hz diag to prove liveness.

Recommended triage sequence (15 minutes)

  1. 1 min — Confirm which binary is flashed. arm-none-eabi-objdump -t build/*.elf | grep WIRE_TEST or check last flash log. If MicroRosEth_CM4_wiretest.elf is flashed, Jetson commands will never work — flash CM4_standalone and retry (#1).
  2. 2 min — Check CM7 serial. Look for CM7: joint-cmd-recv size=… then CM7: joint-cmd-parsed seq=… after publishing from Jetson. Also check the 1 Hz line: mot=seq:… ack:… brk:… f:…. Use this table:
    • seq stays 0 → #5 (QoS) or #7 (magic) or #2 (size reject)
    • seq increments, ack stays 0 → #3 (fault gate) or #6 (cache) or #4 (wrong index)
    • seq==ack increments, no motion → #3/#8/#9
  3. 2 min — Topic audit on Jetson. ros2 topic info /joint_commands -v (QoS), ros2 topic echo /joint_commands --field data (count & values), ros2 topic hz /joint_states (expect ~50 Hz).
  4. 3 min — Manual publish. ros2 topic pub --once /hardware_level/commands sensor_msgs/msg/JointState "{name: [joint_1,joint_2,joint_3], position: [0.5,0,0]}" and watch act:… and physical J1.
  5. 5 min — Fix #2 + #3 first. They cover ~60% of observed failures and are 30 min of code change total; then retest the same manual publish.
