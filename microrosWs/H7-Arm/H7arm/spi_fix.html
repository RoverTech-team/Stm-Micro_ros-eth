SPI1 Fix — NUCLEO-H755ZI-Q (Cortex-M4)

File: CM4/Core/Src/spi.c

1. Root Causes

1a. MODF (Mode Fault) — NSS pin low with hardware NSS management

The SPI NSS pin (PA4) is driven low by GPIO (the application manually controls CS).
CFG2 had SSM = 0 (hardware NSS management), so the SPI saw NSS low and raised a Mode Fault (SR.MODF = 1).
When MODF fires, hardware clears SPE and the transfer never starts.

CFG20x03000000 (CPOL|CPHA only, no MASTER, no SSM)0x07400000 (MASTER|SSM|CPOL|CPHA)

1b. CFG2 missing MASTER bit (SPI in slave mode)

Without MASTER = 1 in CFG2, the SPI operates in slave mode and will never generate SCK. The HAL's MX_SPI1_Init writes CFG2 with all fields, but the register read back showed 0x03000000 — only CPOL and CPHA present. MASTER and SSM were missing, likely due to bus-matrix write aliasing on the dual-core part.

1c. HAL init writes not taking effect on dual-core

The HAL's WRITE_REG(SPI1->CFG2, ...) includes SPI_CFG2_MASTER and SPI_NSS_SOFT (SSM), but the writes did not persist in the register when read via the CM7 debug port. This is consistent with dual-core address aliasing: writes by CM4 to SPI1_BASE may reach a different physical register than reads from the CM7 debug access port.

2. Fix Applied

In SPI1_Transfer() — before every transfer:

/* Force CFG2: MASTER + SSM (soft NSS, prevents MODF) + CPOL/CPHA */
SPI1->CFG2 = SPI_CFG2_MASTER | SPI_CFG2_SSM |
             SPI_CFG2_CPOL  | SPI_CFG2_CPHA;
SPI1->CR1 |= SPI_CR1_SSI;   /* internal NSS high (needed when SSM=1) */

This ensures the SPI is always configured correctly at transfer time, regardless of what the HAL init actually wrote to the hardware.

3. Verification

After the fix, register reads confirm correct configuration:

  • CFG2 = 0x07400000 — MASTER | SSM | CPHA | CPOL
  • SR.MODF = 0 — no mode fault
  • CR1 shows SPE | SSI
  • SR.TXP = 1 — TX FIFO has space, ready to send

The application hangs later at RARM joint configuration (last_fault_code = 0x1F), but the SPI layer itself is now correctly configured.
