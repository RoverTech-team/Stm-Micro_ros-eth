## Motor motion results (tested via `/joint_commands`)
- **J1: does NOT move** — driver stays in HiZ (`0xE203`), `ABS_POS` stays 0.
  SPI reads/writes are healthy (diagonal probe passed for all 6 lanes), so this
  is NOT a bus problem. Suspected: hardware/power-stage issue on J1 specifically
  (motor supply Vs, phase wiring, or latched OCD/UVLO fault). A ratio error
  would still energize the driver and move, so ratios are not the cause here.
- **J2, J3, J4, J5, J6 all move** over ROS.
- **J3 runs away** (unconfigured/fast driver) and does not stop on a 0 command.
- **J5 stalls** in some runs ("too fast it stalls") — SM_16 moves 8× faster
  than SM_128 (0.6 s vs 4.7 s for 10°); acceleration may be too aggressive.

## Ratios are wrong (root cause of position error on moving joints)
- `reduction_ratio` is `uint16_t`. J4/J5 actual ratio is 4.8 but stored as 4
  (truncated) → 20% short. J1=125, J2=50, J3=50, J6=30 are integers and fine.
- Fix options: scaled-integer field (×10 → 48, divide by 10 in step math) or
  hard-coded effective ratio (24/5) in the computation.

## `/joint_states` appears empty
- Type conflict: CM7 publishes `std_msgs/Float32MultiArray`, another node
  publishes `sensor_msgs/JointState`. Use explicit type:
  `ros2 topic echo /joint_states std_msgs/msg/Float32MultiArray`.
- CM7 publishes joint_states **only on command arrival** (not periodic).
- Alternative: read shared memory directly via SWD at offset 0x40
  (`joint_act_positions`).

## Update — J3 stop behavior
- J3 **does stop** when commanded with a tiny non-zero value (0.001 rad), but
  NOT when commanded with exactly 0.0. This confirms the root cause is the
  **reduction ratios being wrong for ALL joints**: the step count is computed
  with a truncated/incorrect ratio, so `RARM_GetPositionMilliDegrees` never
  returns a value matching the commanded target → `delta = cmd - current` is
  never exactly 0 → every command triggers a move → the joint never stops.
  Sending 0.001 makes delta small enough to effectively halt.
- This affects all joints, not just J4/J5. Even the "integer" ratios (J1=125,
  J2=50, J3=50, J6=30) may be slightly off or the step math has a rounding
  issue that accumulates.
- **Priority fix**: correct all reduction ratios and the step computation so
  that a 0.0 command produces delta=0 and the joint holds.

## Clarification — ratio error magnitude
- With a 0.01 rad command, J3 moves ~20° then stops. The movement is ~35× too
  large for the command, confirming the reduction ratio (or step math) is
  severely wrong for all joints. A 0.001 command barely moves (effectively stops).
- The ratio error is not a small truncation (4.8→4) — it is large enough to
  cause massive overshoot. Likely the ratios are inverted, off by an order of
  magnitude, or the step formula has a unit error (mdeg vs deg, or steps_rev
  mismatch).
- **Priority #1 fix**: re-derive and correct ALL reduction ratios and verify the
  step computation formula in `RARM_MoveMilliDegrees` against the wiretest
  (which worked with SM_16 and the reference setups.h values).
